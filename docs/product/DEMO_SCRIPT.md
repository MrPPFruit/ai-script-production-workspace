# 3 分钟演示脚本：《暴风雨》从来源到部门任务材料

> 状态：**MVP canonical**
> 本脚本演示确定性数据和产品工作流，不宣称实时模型效果，也不模拟任务已经送达真实部门。

## 演示准备

- 默认项目：The Tempest / 《暴风雨》；正式 Demo 从样本第 1 项 ACT I, SCENE I 开始。
- 默认来源：已记录出处的公版英文短场次；中文为项目自译并明确标注。
- V1 场次：ACT I, SCENE I；ACT I, SCENE II；ACT III, SCENE III。
- V2 预置变化：项目内演示改编版把 ACT III, SCENE III 拆成 III-A“岛上宴席出现”和 III-B“鹰身女妖揭示”，并加入“实物宴席桌 + 实时合成宴席影像”的演示性动作与制作注。
- 预置对象：Ariel 角色实体；一条风暴制作建议；一条宴席/VFX 相关任务材料草稿。

## 必讲边界

- 《暴风雨》是用户已确认的默认剧本；场次短样本使用已记录来源的公版英文文本，不使用未核验中文译本。
- 角色、场景、道具、VFX 是 Demo 覆盖类型，不是完整行业分类树。
- AI/模拟数据只提供受规范建议；制片人工采用或关联后才形成实体。
- 任务产物是“面向部门的材料草稿”，不是已送达任务。
- V2 只演示场次—实体关系影响；真实下发后的更新、撤回、回执和通知明确 DEFERRED。

## 可能追问

### Q1：为什么没有做任务下发后的更新或撤回？

因为“下发”不是一个按钮，而是跨参与者的状态承诺。要诚实实现，必须先定义收件人身份、部门主管与个人的权限、通知渠道、送达和回执、谁能撤回、旧任务如何失效、审计记录，以及多个渠道和离线副本如何保持一致。录音也明确把这部分排除在本题外，所以 MVP 停在未下发草稿，并在版本变化时提示“发布前复核”。

### Q2：四类实体是面试官指定的吗？

不是。录音要求实体体系受规范并能对接部门，角色、场景、道具和特效只是被提到的例子。本 Demo 用四类覆盖关键路径，但不把它们宣称为完整或冻结的 taxonomy。

### Q3：为什么不保留“原文明确/生产推断”的完整二元状态机？

录音没有规定这套状态机。更小且足够的方案是每条建议都展示原文锚点；非字面制作需求再显示“制作判断”。这样既能解释隐含 VFX，又不增加一套与用户结果无关的状态。

### Q4：为什么不用实时模型？

本题验收交互、信息组织与生产闭环，不验收模型质量。确定性数据能稳定证明链路，也避免把演示成败交给供应商响应。真实模型接入应在工作流价值成立后另行评测。

### Q5：场次变了，实体会跟着重建吗？

不会。实体保持稳定，变化主要落在带版本的场次—实体关系。V2 先显示影响，再由制片更新关系；系统不做通用自动继承，也不静默覆盖 V1。

### Q6：这比 Excel 多了什么？

重点不是界面形式，而是关系和责任边界：来源锚点、规范实体、Metadata、跨场关系、部门材料和版本影响属于同一条可追溯链。Excel 也可承载这些信息，但通常需要人工维护多张表之间的一致性。
