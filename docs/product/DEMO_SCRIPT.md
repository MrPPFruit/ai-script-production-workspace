## 演示准备

- 通过私有部署数据或本地导入加载第四幕本次导入全文；公开仓库不依赖正文。
- 导入配置包含 3–4 个幕内处理单元，并显示实际数量。
- 处理单元按人物进退场和关键舞台指示划分，只服务 API 限长、进度和失败隔离，不是原作场次。
- 正式环境在服务端配置 DeepSeek；不显示任何凭证。
- 预置建议明确标为“示例数据 / 尚未调用 DeepSeek”；fallback 不得冒充 DeepSeek。
- 默认 fixture 分类修正已在 `334b0bd` 验收：人物关系使用 `cast`，默认数据不含 `other`。

## fallback 演示口径

若某个处理单元返回 fallback：

1. 不把它说成 DeepSeek 成功；
2. 展示该单元的原因码；
3. 使用同一处理单元的确定性建议进入审阅；
4. 强调 fallback 只保障工作流；
5. 不做隐藏重试。

逐单元确定性 fallback 已实现；正式 Demo 仍必须另行通过真实 DeepSeek 全单元浏览器链。

## 必讲边界

- “完整文本”是第四幕本次导入全文，不是整部《雷雨》。
- 原作来源层是第四幕；3–4 个处理单元不是原作场次。
- 处理单元数量是 Demo 实现选择，不是录音规定或自动算法结果。
- 精确 quote/range 比处理单元更细。
- 点击 evidence 只导航/高亮，不触发新 AI。
- 人工采用/关联/忽略是唯一实体写入边界。
- `cast` 显示“人物关系”；`other` 只显示“待分类”，默认 fixture 不使用。
- 任务的五类制作字段可编辑，来源、版本和未下发状态锁定。
- 不实现镜头级拆分。
- 版本只演示一次单元插入/切分关系复核，不宣称通用继承。
- 任务材料仍未下发。
- 版权不阻塞面试 Demo 选用；公开仓库正文策略由交付阶段单独处理。

## 可能追问

### Q1：为什么不用“场次”？

《雷雨》原作按幕组织，本次来源层是第四幕。3–4 个单元是系统为接口限长、进度和失败隔离建立的处理单元；称为原作场次会制造不存在的来源结构。

### Q2：为什么是 3–4 个处理单元？

这是本次导入样本的工程范围，由人物进退场和关键舞台指示形成可读边界。录音没有规定算法或固定数量，所以产品显示实际配置，不把数量写成行业规则。

### Q3：为什么显示全文却按处理单元调用？

全文解决制片阅读上下文；处理单元控制输入大小和失败范围。精确 evidence 再把 AI 结果锚回全文。

### Q4：为什么不做到镜头级？

录音把镜头列为可调整/实体化的例子，没有要求本次 Demo 必须完成镜头拆分。加入镜头级会引入另一套拆分和关系合同，不能直接提升核心链可信度。

### Q5：文本片段为什么不直接成为实体？

文本是来源，实体是经过制片确认的稳定生产对象。直接实体化会把重复出现的人物、道具或效果拆成大量不稳定对象。

### Q6：公开仓库会包含《雷雨》正文吗？

选剧本与代码公开是两个决策。当前正文通过私有部署数据或本地导入加载，公开仓库不提交；最终交付如需调整再单独确认。

### Q7：为什么不直接在当前剧本上修改？

原地覆盖会让旧 evidence、实体来源和任务快照失真。正确流程必须创建编辑提案和新 ScriptVersion，记录 diff，只重分析受影响单元，再由人工复核。本轮 UI 只说明该流程，不实现直接改写。
