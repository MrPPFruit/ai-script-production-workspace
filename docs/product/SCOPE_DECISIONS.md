# MVP 范围决策

> 状态：**canonical**
> 用途：区分录音事实、用户确认和产品选择，防止把候选机制包装成既定要求。

## 1. 决策层级

| 层级 | 含义 | 本轮处理 |
| --- | --- | --- |
| 录音高置信 | INTERVIEW_EVIDENCE_MATRIX.md 中有直接证据 | 作为产品核心，不降级 |
| 用户已确认 | 本轮明确确认，但不一定来自录音 | 作为项目决策，注明来源 |
| MVP 产品选择 | 为实现核心结果而选的最小机制 | 可进入规格，但不得称为面试官要求 |
| DEFERRED | 价值或边界未验证，或完整能力超出 Demo | 不进入本次实现/验收 |

### 文档优先级

- PRODUCT_SPEC.md、SCOPE_DECISIONS.md 与当前 OpenSpec 是产品范围的 canonical。
- INTERVIEW_EVIDENCE_MATRIX.md 是证据层；CLASSIC_SCRIPT_CANDIDATES.md 是选材研究。
- VISUAL_OPTIONS.md、DEFAULT_SCRIPT_SELECTION.md 是历史探索，不拥有当前范围决定权。
- roadmap.md 中“可下发”只表示材料结构具备进入后续派发流程的条件，不表示本 Demo 已完成真实发送。

## 3. 录音不支持项的处理

| 原先被写成既定要求的内容 | 证据结论 | 本轮决定 |
| --- | --- | --- |
| 角色/场景/道具/VFX 是固定且完整分类树 | 录音只要求受规范、与部门结合，并把这些作为例子 | 降级为 Demo 覆盖集；taxonomy 可扩展 |
| 每条建议必须有“原文明确/生产推断”二元标签 | 录音支持隐含制作需求，但未规定标签/状态机 | 删除完整二元状态机；保留来源锚点 + 必要时的制作判断 |
| 编辑/合并/确认/拒绝是完整人审状态机 | 录音只明确“方便调整、创建实体” | 简化为采用新实体、关联既有、忽略 |
| V1/V2 自动 diff、保留/合并/新建是既定规则 | 录音只支持场次/实体继承问题 | 使用确定性影响数据和一次人工关系复核，不承诺算法 |
| 已下发任务要自动更新、撤回或标记复核 | 录音 E-06 明确排除 | DEFERRED；MVP 不存在“已下发”状态 |
| 本题的 Extractor 是或不是 Agent | Agent 讨论属于前一个案例，未绑定本题 | 从验收要求删除；MVP 不提供 Agent 能力 |
| 必须接入 DeepSeek 或真实模型 | 录音明确 AI 可模拟且不考模型质量 | DEFERRED；确定性数据为唯一必需路径 |
| 必须接入真实项目管理/通知系统 | 录音讲产品价值与项目管理绑定，但初步 Demo 不要求真实集成 | DEFERRED；Demo 只表达项目和部门语境 |

## 4. 任务真正下发后的更新/撤回：NO-GO

### 第一性原理判断

真正下发意味着系统对另一个人作出“你已收到并应执行某个版本要求”的承诺。只增加“更新”或“撤回”按钮，无法兑现这个承诺。

完整能力至少需要：

| 维度 | 必须回答的问题 | 缺失时的失败 |
| --- | --- | --- |
| 收件人 | 接收者是部门、主管还是具体人员？人员变化如何处理？ | 系统不知道谁应停止旧工作 |
| 通知渠道 | 站内、邮件、企业 IM 或第三方项目系统哪个是权威渠道？ | 页面更新了，接收者仍执行旧消息 |
| 送达与回执 | 如何区分已发送、已送达、已读、已确认、已开工？ | “撤回成功”没有业务意义 |
| 权限 | 谁能修改、撤回、拒绝或重新下发？ | 任意修改可能破坏生产责任 |
| 审计 | 是否保留旧任务、变更人、时间、原因和确认记录？ | 无法追责，也无法还原当时要求 |
| 旧任务失效 | 旧版本如何显著失效？已开工或已产生成本怎么办？ | 新旧要求并存，造成返工或损失 |
| 一致性 | 多渠道、离线副本、重试和并发修改如何收敛？ | 不同接收者持有不同“最新版本” |

结论：这是一套多参与者、跨渠道、带审计和补偿机制的分布式工作流，不是低复杂度 UI 增强。它不服务本次录音验收，故本次 **NO-GO / DEFERRED**。

### MVP 更小替代

- 任务产物只称“部门任务材料草稿”，不出现已发送、送达、已读、回执或撤回状态。
- 草稿保存创建时的剧本版本和来源摘要。
- V2 变化只对相关草稿显示“来源已变化，发布前复核”。
- 用户可以返回草稿补充材料，但系统不声称已通知任何真实接收者。

### 何时重新开启

只有同时明确首个真实接收角色、权威下发渠道、状态机、权限与审计规则，并能处理已开工任务的补偿策略时，才重新立项。

## 5. 低复杂度附加项

| 候选 | 用户价值 | 实现/认知成本 | 决策 | Ponytail 更小方案 |
| --- | --- | --- | --- | --- |
| Metadata 缺口提示 | 制片能立刻发现部门材料还缺什么 | 低；按预置必需字段判断 | GO | 只列缺失字段，不做置信分或复杂评分 |
| 跨场次来源跳转 | 资产统筹能核对复用是否合理 | 低；复用既有关系与锚点 | GO | 数量 + 链接，不做节点图 |
| 按部门分组与数量 | 制片能快速看到部门工作面 | 低；视图层分组 | GO | 部门标题内联数量，不做 dashboard |
| 批量确认/批量改写 | 小样本中收益有限，误操作代价高 | 中；需要选择、撤销、冲突规则 | NO-GO | 逐条处理；真实批量规模出现后再验证 |

## 6. 对实现的硬边界

- 任何页面或文档不得把确定性建议描述为实时模型结果。
- 任何页面或文档不得把任务材料草稿描述为已下发、已送达或可撤回。
- 任何版本变化不得静默改写 V1 来源、实体关系或草稿快照。
- 四类 Demo taxonomy 不得被描述为完整行业标准。
- 不因已存在按钮或类型而把已降级能力重新带回 MVP。
