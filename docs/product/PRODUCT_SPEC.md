# 《雷雨》·面试 Demo 导入版本（第四幕）：AI 剧本生产工作台

> 状态：**MVP canonical**
> 当前唯一用户可见主目标：DeepSeek 真实顺序处理第四幕导入版本的 3–4 个幕内处理单元，并把通过服务端结构与原文证据校验的建议送入人工审阅。
> “完整文本”仅指本次导入的第四幕全部文本，不代表整部《雷雨》。

## 1. 产品结论

这是面向制片统筹、执行制片和资产统筹的 AI 剧本生产工作台。它把剧本中的生产线索转成带原文证据、可人工决策的建议，再沉淀为带 Metadata 的稳定生产实体和未下发部门任务材料。

面试官网页唯一主链：

> 第四幕导入全文 → DeepSeek 顺序处理 → 精确证据与 AI 建议 → 人工编辑/采用/关联/忽略 → 稳定实体 → 部门任务材料草稿 → 一次版本影响人工复核

模型质量不是本次考核重点，但真实 DeepSeek 调用进入用户主链是必须验收的能力。fallback 只承担明确保障，不能替代主链。

## 2. 出题官考察点

- 能否把 AI 拆解从展示性标签推进到可追溯的实体和部门任务材料。
- 能否用精确原文 evidence 区分剧本明确事实与生产推断。
- 能否把人工编辑、采用、关联和忽略设计为可信写入边界。
- 能否在重新分析或来源边界变化时避免静默覆盖历史结果。
- 能否诚实区分已实现 API、尚未接线的产品链和未来路线图。

## 3. 用户、JTBD 与问题

| 用户 | 本次角色 | 核心需要 |
| --- | --- | --- |
| 制片统筹 | MVP 主操作人 | 从连续剧本文本中整理统一实体和跨部门任务材料 |
| 执行制片 | 次要使用者 | 核验生产要求、来源和版本影响 |
| 资产统筹 | 次要使用者 | 复用跨文本区段实体，避免重复建档和关系漂移 |

JTBD：当我接到一版剧本并要组织制作准备时，我想让 AI 给出带精确原文证据的生产建议，再由我校订、建立实体并组织部门任务材料，从而减少重复整理，并在重新分析或文本边界变化时保留人工决定和历史关系。

核心问题：

- 只看孤立文本片段会丢失第四幕连续阅读上下文。
- 自由文本 AI 输出缺少受控分类、精确证据和稳定消费方式。
- 隐含 VFX、声音、灯光等制作需求未必包含对应字面词。
- 同一人物、道具或需求重复出现时容易被重复建档。
- fallback 若不披露，会制造虚假的“AI 成功”。
- 重新分析或版本变化若原地覆盖，会破坏人工决定、实体和任务快照。

## 4. 内容与来源边界

- 产品显示名称固定为 **《雷雨》·面试 Demo 导入版本（第四幕）**。
- 阅读区连续显示本次导入的第四幕全部文本，不声称覆盖整部《雷雨》。
- 原作按“幕”组织；官网页不得人为编造原作场次编号。
- AI 为接口限长、进度和失败隔离，把第四幕预先配置为 3–4 个幕内处理单元。它们不是原作场次，页面只显示实际配置数量。
- 每条建议必须锚定比处理单元更细的精确原文 quote/range。
- 本 Demo 仅供面试官查看；记录作品、作者、导入版本、第四幕来源和使用边界即可，版权不再阻塞选剧本。
- 公开 GitHub 是否包含正文与选剧本分开决策。当前正文由私有部署数据或本地导入加载，公开仓库不提交正文。

为避免误解，来源层级只保留最小合同：SourceSection 是第四幕导入全文；AnalysisUnit 是 3–4 个系统处理单元；EvidenceSpan 是建议引用的精确原文；人工采用或关联后才形成稳定 Entity 和来源 Relation。不能把处理单元称为原作场次，也不能把每个文本片段直接变成实体。

## 5. 录音证据边界

录音明确要求场次、镜头、道具等生产要素可以调整，调整结果可以建实体并挂 Metadata，并以“10 场变 11 场”举例说明插入/切分影响。

录音没有规定拆分算法、固定数量、镜头级必须实现或通用自动继承。因此：

- 3–4 个处理单元是本 Demo 的工程选择，不是原作结构或录音硬要求；
- 本次不实现镜头级拆分；
- 版本能力只演示一次处理单元插入/切分导致来源关系需要人工复核。

### 完整文本交互

- 中间区始终显示第四幕导入全文，不用当前处理单元替换全文。
- 点击处理单元只滚动到对应锚点。
- 点击建议/evidence 会切换到建议所属版本，滚动并高亮精确 quote。
- 点击证据只改变阅读位置和高亮，不触发新 AI 或生产写入。
- 切换版本后必须按该版本重新定位证据，不能复用旧字符偏移。

## 7. AI Workflow 与诚实状态

客户端按配置顺序逐个调用现有单次 API，前一单元结束后才处理下一单元。

> 准备队列 → 当前单元请求 DeepSeek → 服务端结构/证据校验 → deepseek 或 fallback 待审 → 下一单元

用户可见状态只包括等待、请求中、DeepSeek 已校验待审、fallback 待审或失败。不得伪造“正在识别角色”“正在分析道具”等模型内部阶段。

每条建议必须包含受控 taxonomy、名称、evidenceKind、confidence、至少一个精确 quote/range，以及 inferred 建议的制作判断理由。服务端确认 quote 是当前处理文本的逐字子串并重算范围；客户端再映射到第四幕全文。

现有 API 的 sceneId/title/text 可以继续作为内部兼容字段，分别承载处理单元 ID、显示名和文本。本次不做大规模接口改名；但官网文案和 canonical 统一使用“处理单元”，并保留 sourceSection=第四幕。

fallback 必须显示原因，并使用当前处理单元的确定性建议进入同一审阅链。当前通用单条 fallback 仍未满足正式 Demo。

## 8. HITL、实体与任务草稿

AI 只能建议。用户可以：

- 编辑建议；
- 采用为新实体；
- 关联到既有实体；
- 忽略。

SuggestionBatch 在人工决定前不是生产事实。ProductionEntity 使用稳定 ID，不能按文本片段数量自动创建。实体来源关系可以保留第四幕、处理单元和精确 evidence；同一实体可关联多个证据。

TaskMaterialDraft 只从人工确认实体生成，按角色部、场景部、道具部、VFX 等部门组织，并保存实体、版本、来源证据和制作要求快照。状态必须明确为未下发，不得伪造收件人、送达或回执。

## 9. 重新分析与版本影响

- 重新分析当前单元或全部单元只创建新的 AiRun/SuggestionBatch。
- 旧批次、人工决定、实体和任务草稿保持不变。
- V2 只演示一次处理单元插入/切分：受影响实体来源关系显示旧新单元和证据，等待人工重连或保留。
- 不宣称通用自动继承、通用剧本 diff 或原作场次自动重建。

## 10. MVP 与明确不做

MVP 包含：

- 第四幕导入全文与锚点导航；
- 3–4 个处理单元的 DeepSeek 顺序批处理；
- 精确 evidence 高亮；
- AI 建议与 HITL；
- 稳定实体与部门任务草稿；
- 一次处理单元插入/切分关系复核；
- fallback、来源与使用边界的诚实披露。

明确不做：

- 镜头级拆分；
- 自动处理单元拆分算法；
- 任意长剧本的生产级批处理；
- 通用自动分场、通用 diff 和自动关系继承；
- 反向修改剧本、Git 式版本、选中文字触发新 AI；
- 真实任务派发、更新、撤回；
- 模型质量评测、多用户、预算和完整项目管理。

## 11. 成功标准

| ID | Observable | Counterexample | Evidence |
| --- | --- | --- | --- |
| AIWF-01 | 一次 run 严格顺序处理实际 3–4 个处理单元 | API 存在但 UI 未调用，或漏单元却称全部 | 请求数等于导入配置且摘要一致 |
| AIWF-02 | 用户看到当前处理单元和最终 deepseek/fallback | 使用“原作场次”误导，或展示假模型阶段 | 浏览器状态与文案检查 |
| AIWF-03 | 每条待审建议都有精确 quote/range | 只有单元级来源，或 quote 不在正文 | API 正反例与范围映射测试 |
| AIWF-04 | fallback 使用本单元确定性建议且原因可见 | fallback 冒充 DeepSeek 或只有通用占位 | 失败矩阵与 UI 模式检查 |
| AIWF-05 | 编辑后可采用新实体、关联既有或忽略 | AI 自动写实体，或文本片段直接实体化 | 浏览器人审链 |
| AIWF-06 | 第四幕导入全文常驻；单元/建议点击定位精确高亮 | 只显示单元文本、跳错版本或无联动 | 全文锚点与滚动高亮检查 |
| AIWF-07 | 稳定实体保留精确来源并生成未下发部门草稿 | 实体仅引用粗粒度来源或任务伪造送达 | 关系与任务快照断言 |
| AIWF-08 | 一次单元插入/切分显示关系影响并等待人工复核 | 静默覆盖或宣称通用自动继承 | 旧新关系对照与复核操作 |
| AIWF-09 | 重新分析只新增 run/batch | 覆盖人工决定、实体或任务 | 两次 run 前后对照 |
| AIWF-10 | 标题、全文范围、处理单元和使用边界诚实，主 UI 无死按钮 | 把单元称原作场次、冒充整部原作或出现死按钮 | 内容盘点、仓库正文检查与控件遍历 |

## 12. 风险与后续思考

| 风险 | 当前控制 |
| --- | --- |
| 处理单元冒充原作结构 | 官网统一称“处理单元”，来源固定为第四幕 |
| AI 来源只到粗粒度文本 | 每条建议强制精确 quote/range |
| 文本片段直接实体化 | 实体只由人工决定产生，来源通过关系保留 |
| API 兼容名泄露到 UI | 仅在适配层映射，不重构服务端字段 |
| fallback 冒充模型 | mode/reason 强制披露 |
| 版本能力被夸大 | 只验收一次单元插入/切分关系复核 |
| 公开仓库正文边界混淆 | 当前正文私有/本地加载，最终交付单独决定 |

后续路线只在静态产品边界中说明：自动拆分、镜头级生产结构、任意剧本导入、多人协作、真实任务派发与模型质量运营。
