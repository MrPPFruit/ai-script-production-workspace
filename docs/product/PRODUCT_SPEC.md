# AI 剧本生产工作台：产品规格

> 状态：**MVP canonical**
> 证据优先级：录音高置信结论 → 用户已确认的项目决策 → 本文明确标注的 MVP 产品选择。不得把后两类包装成面试官原话。详细边界见 SCOPE_DECISIONS.md。

## 1. 产品结论

这是一个面向制片侧的剧本生产工作台。它不以“AI 拆出了多少标签”为交付，而是帮助制片统筹把剧本和场次中的生产线索，整理成受规范、带 Metadata、可追溯的生产实体，再形成面向部门主管的任务材料草稿。

唯一主链：

> 剧本版本与场次来源 → 受规范的 AI/模拟建议 → 人工调整并采用或关联 → 稳定生产实体及 Metadata → 部门任务材料草稿 → 场次/实体版本关系复核

本次验收产品链路和信息组织，不验收模型质量。确定性演示数据是主路径。

## 2. 出题官考察点

录音高置信支持的考察点是：

1. 是否真正围绕制片统筹、执行制片或资产统筹的工作，而不是导演创作或通用剧本阅读。
2. 是否把拆解接入生产管理语境，让场次、角色、道具、视效等元素成为有 Metadata 和关系的实体。
3. 是否能把实体组织成制作部门看得懂的任务材料，而不是停在标签清单。
4. 是否考虑文本未直说、但制作上需要处理的隐含 VFX/声音/灯光等需求。
5. 是否能解释剧本变化后场次与实体关系如何受影响。
6. 是否用一个初步 Demo 清楚证明交互和呈现；AI 可以模拟，模型准确率不在本次考核内。

完整的任务下发、通知、回执、撤回及下发后更新不在录音要求内，也不属于本次 MVP。

## 3. 用户与 JTBD

### 主要用户

| 用户 | 本次角色 | 核心需要 |
| --- | --- | --- |
| 制片统筹 | MVP 主操作人 | 把剧本生产信息转成统一实体与跨部门任务材料 |
| 执行制片 | 次要使用者 | 核验生产要求、时间语境和受版本变化影响的内容 |
| 资产统筹 | 次要使用者 | 复用跨场次实体，避免重复建档和关系漂移 |

导演不是本产品的主操作用户；部门主管是任务材料的目标读者，但 MVP 不实现其独立收件端。

### JTBD

当我接到一版剧本并要组织制作准备时，我想从具体场次和原文线索出发，快速校准 AI/模拟生成的生产建议，将其沉淀为带上下文的实体和部门任务材料，从而减少重复整理，并在剧本改版时知道哪些场次—实体关系需要重新确认。

## 4. 问题

以下问题中，“孤立拆解不能形成生产闭环”有录音直接支持；关于重复整理、口径漂移和表格维护成本的描述是待真实制片验证的产品假设，不冒充访谈事实。

- 孤立拆解只产生标签，制片仍需在表格或项目系统中重新建实体、补上下文和分部门。
- 自由生成的 AI 分类和字段不可控，难以长期汇总，也无法成为可靠的生产记录。
- 隐含制作需求往往不含“特效”等字面词；只做关键词提取会漏掉真正影响制作的判断。
- 同一角色、道具或制作需求可能跨场次出现；若每场单独建条目，会形成重复资产与口径漂移。
- 剧本改版会改变场次编号、切分和来源文字；若关系被静默覆盖，制片无法判断哪些实体仍然有效。
- 若把任务草稿展示成“已下发”，却没有收件人身份、通知、回执、权限和审计，Demo 会制造虚假完成感。

## 5. 目标与非目标

### MVP 目标

- 使用默认剧本《暴风雨》的少量公版英文场次，证明从来源到部门任务材料的最小闭环。
- 在项目预置的实体体系内呈现 AI/模拟建议，并显示其原文锚点和制作判断。
- 允许制片人工调整建议，采用为新实体、关联到既有实体或忽略。
- 让生产实体保留稳定 ID、规范类型、关键 Metadata、来源场次和版本关系。
- 从实体生成按部门组织、尚未下发的任务材料草稿。
- 用一个确定性 V2 案例显式展示场次/实体关系变化及受影响的任务材料草稿。

### 非目标

- 真实任务下发、收件人端、通知、回执、撤回、下发后更新或跨渠道一致性。
- 完整项目管理、个人派工、预算、排期计算、采购、权限、多人实时协作或数据库持久化。
- 完整或自动化的剧本 diff、实体继承和冲突合并算法。
- 模型准确率评测、特定供应商接入或实时模型作为演示依赖。
- 把四类 Demo 类型宣称为完整行业分类树。
- AI Agent、自动工具规划、自动写入实体或自动发布任务。

## 6. 默认剧本与演示内容

默认剧本固定为 William Shakespeare 的《暴风雨》（The Tempest）。英文原文采用 [MIT Shakespeare — The Tempest](https://shakespeare.mit.edu/tempest/) 明示 public domain 的 HTML 版本，并记录逐场 URL、取得日期和片段边界；中文为项目依据这些英文片段制作并显式标注的演示自译，不使用未核验第三方中文译本。

首版建议使用：

- **样本第 1 项 / 默认初始态：ACT I, SCENE I — On a ship at sea。** 海上风暴提供雷电、风浪、船员与紧急制作线索。
- **样本第 2 项：ACT I, SCENE II — Before Prospero's cell。** Prospero、Miranda、Ariel 与岛屿语境提供跨场角色和魔法制作判断。
- **样本第 3 项：ACT III, SCENE III — Another part of the island。** 宴席出现/消失及雷电舞台指示提供道具、场景、声音/灯光与 VFX 的关联案例。

V2 明确标识为“项目内演示改编版”：它把 V1 的 ACT III, SCENE III 拆成 ACT III, SCENE III-A“岛上宴席出现”和 ACT III, SCENE III-B“鹰身女妖揭示”，并实际加入“实物宴席桌 + 实时合成宴席影像”的演示性动作与制作注。它不是 Shakespeare 原作的新版本，也不只是制作方案字段变化；只用于展示场次切分后哪些实体关系需要复核，不代表系统已实现通用版本匹配算法。

## 7. 信息架构

| 区域 | 核心内容 | 目的 |
| --- | --- | --- |
| 项目与版本 | 项目名、剧本名、当前版本、演示数据标识 | 建立当前工作上下文 |
| 场次与来源 | 场次列表、原文片段、来源定位 | 让建议和实体可回到剧本证据 |
| 生产建议 | 规范类型、建议名称、原文锚点、制作判断、待补 Metadata | 供制片校订，不作为系统事实 |
| 生产实体 | 稳定 ID、标准名、类型、Metadata、跨场次关联 | 形成可复用的生产口径 |
| 部门任务材料 | 负责部门、制作要求、实体、场次、版本、准备窗口、来源摘要 | 在下发前形成可审阅材料 |
| 版本关系影响 | V1/V2 来源变化、受影响关系及任务材料提示 | 防止静默覆盖 |

## 8. 主用户链

1. 制片统筹进入《暴风雨》项目，选择剧本版本与场次。
2. 用户从原文锚点查看一条受规范的 AI/模拟建议；隐含需求同时展示“为何形成此制作判断”。
3. 用户修订名称、部门、制作要求或 Metadata。
4. 用户选择“采用为新实体”“关联到既有实体”或“忽略”。采用或关联后，建议才进入生产实体体系。
5. 用户打开实体，核对跨场次来源和 Metadata 完整度。
6. 用户从实体生成部门任务材料草稿；草稿保持“未下发”，并保留创建时的剧本版本与来源摘要。
7. 用户切换到确定性 V2 影响视图，查看场次—实体关系变化和受影响草稿，再人工调整关系或返回草稿补充材料。

## 9. AI 与 HITL 原则

### 受规范的建议

- 项目提供预置的 Demo taxonomy；角色、场景、道具、VFX 是演示覆盖类型，不是完整且冻结的行业分类树。
- 每条建议都必须有原文锚点；若制作要求不是原文字面事实，还必须展示简短制作判断。
- AI 或确定性数据只能产生建议，不能直接成为实体、修改既有关系或发布任务。
- 本次不要求独立的“原文明确/生产推断”二元状态机；“来源原文 + 制作判断”已经提供更直接的可核验边界。

### 人工决策

- 制片可以调整建议，再将其采用为新实体或关联到既有实体；相似名称不得自动合并。
- “确认/拒绝/合并”不是录音规定的完整工作流。MVP 以“采用新实体 / 关联既有 / 忽略”表达最小且充分的结果状态。
- 所有实体和关系变化必须来自显式人工操作，并保留来源版本。

### AI/Agent 边界

录音没有要求本题提供 Agent，也没有把本题某个 Extractor 定义为或否定为 Agent。MVP 只提供受规范的建议来源，不提供自主工具调用或自动写入；Agent 能力整体延后。

## 10. 实体与任务材料模型

| 对象 | MVP 最小字段 | 关键约束 |
| --- | --- | --- |
| ScriptVersion | versionId、名称、来源、取得日期 | 版本不可静默覆盖 |
| Scene | sceneId、幕/场、标题、原文片段、versionId | 场次编号和关系允许随版本变化 |
| SourceAnchor | anchorId、片段、场次、定位 | 建议、实体和任务材料可反向追溯 |
| Suggestion | suggestionId、规范类型、名称、来源锚点、制作判断、拟议 Metadata | 仅为待人工处理的建议 |
| ProductionEntity | entityId、标准名、类型、Metadata | 稳定实体与版本化场次关系分离 |
| SceneEntityRelation | relationId、entityId、sceneId、versionId、来源锚点、状态 | V2 变更主要作用于关系，不直接改写实体 |
| TaskMaterialDraft | draftId、部门、entityId、制作要求、场次/版本快照、准备窗口、来源摘要、状态 | 状态仅为草稿/需复核；不代表已送达 |
| VersionImpact | impactId、V1/V2 差异、受影响关系、受影响草稿、处理结果 | 确定性 Demo 数据，必须等待人工处理 |

Demo taxonomy 覆盖角色、场景、道具、VFX 四类，以便展示跨部门链路；产品定义保持可扩展，不将四类写成行业完整口径。

## 11. 版本策略

1. ScriptVersion 与 Scene 不可变保存；V2 不覆盖 V1 原文或场次。
2. ProductionEntity 保持稳定，SceneEntityRelation 按剧本版本记录。
3. V2 影响只显示确定性预置差异，不承诺通用自动匹配。
4. 影响视图必须显示变更前后来源、受影响实体关系和相关任务材料草稿。
5. 用户确认前，不更新关系或草稿。
6. 草稿受影响时只标记“来源已变化，发布前复核”；不模拟已下发任务的更新或撤回。

## 12. MVP 附加项

核心之外只保留三个高价值、低复杂度增强：

- **GO：Metadata 缺口提示。** 在实体与任务材料中直接标出缺少的关键字段；不做复杂评分。
- **GO：跨场次来源跳转。** 实体显示关联场次数量，并可回到具体来源；不做关系图谱。
- **GO：按部门分组与数量。** 任务材料按部门主管视角分组，并显示简单数量；不做统计看板。
- **NO-GO：批量操作与自定义看板。** 小样本 Demo 中收益低且增加选择、撤销和状态一致性；更小替代是部门标题内的内联数量。

## 13. 成功标准

| Acceptance | 用户可观察结果 | 反例：局部通过但产品失败 | 最小证据 |
| --- | --- | --- | --- |
| AIR-01 | 用户从《暴风雨》具体场次和来源锚点出发，调整一条建议并采用为实体或关联既有实体 | 页面有 AI 卡片，但无法追溯原文，或调整不影响实体 | 浏览器完成一条来源—建议—实体链 |
| AIR-02 | 实体带 Metadata 和跨场次关系，并能生成含部门、制作要求、版本和来源摘要的任务材料草稿 | 只有实体名或部门标签，没有制作上下文与可追溯关系 | 从实体生成并检查一条部门草稿 |
| AIR-03 | V2 显式显示场次—实体关系变化及受影响草稿，且确认前不改写 V1 | 只换版本号、静默覆盖关系，或声称更新了已下发任务 | 完成一次关系复核并检查 V1 保留 |
| AIR-04 | Demo 用确定性数据稳定演示，并清楚披露“不验收模型质量、未真实下发” | 把模拟结果冒充实时模型，或把草稿称为已送达任务 | 无模型凭证运行核心链并阅读边界说明 |

体验目标：未参与设计的观察者应能在三分钟后回答“谁在用、某项制作要求来自哪一场、形成了什么实体、给哪个部门、V2 改了哪条关系”，且不会误以为系统已经向真实接收者下发或撤回任务。

## 14. 风险与后续路线

| 风险 | 当前控制 |
| --- | --- |
| AI 建议被误当剧本事实 | 强制显示来源锚点；非字面需求显示制作判断 |
| Demo 四类被误解为完整 taxonomy | 明示仅为 Demo 覆盖集，后续需由项目规范配置 |
| 同名实体错误归并 | 只允许人工关联到既有实体 |
| V2 关系被静默覆盖 | 版本化关系、显式影响、确认前只读 |
| 草稿被误认为已下发 | 状态仅为草稿/需复核，不出现送达、回执或撤回承诺 |
| 公版原作与数字文本/译本边界混淆 | 记录来源和场次边界；不使用未核验中文译本 |

后续路线按证据推进：

1. 先用 Demo 验证制片是否理解并愿意采用实体、Metadata 和部门任务材料。
2. 再验证真实项目的 taxonomy、字段必填口径和部门接收材料。
3. 只有确认真实派发渠道、角色权限和审计规则后，才设计任务下发。
4. 只有完成多渠道送达、回执、失效和补偿机制设计后，才评估下发后更新/撤回。
5. 模型接入与质量评测在工作流价值被验证后另立范围。
