AI 剧本生产工作台｜面试官产品手册

面试 Demo：《雷雨》·面试 Demo 导入版本（第四幕） 本手册是面试官入口，说明产品价值、可演示链路与真实完成度。详细产品合同见 PRODUCT_SPEC.md，范围决策见 SCOPE_DECISIONS.md，逐秒演示口径见 DEMO_SCRIPT.md。

1. 一句话定位

面向制片统筹、执行制片和资产统筹，把连续剧本中的制作线索转为带原文证据、经人工确认的稳定生产实体和未下发部门任务材料草稿。

目标用户与 JTBD

用户 核心任务
制片统筹（主用户） 从一版剧本中统一整理人物、场景、道具、声音、VFX 等制作对象和跨部门材料
执行制片 核验制作要求、来源、优先级和版本影响
资产统筹 复用稳定实体，避免同一生产对象被重复建档

JTBD：当我接到一版剧本并开始制作准备时，我希望 AI 先找出带精确原文证据的生产建议，再由我编辑、采用、关联或忽略，最后形成可追溯的实体和部门材料；剧本变化时，系统应显式告诉我哪些关系需要复核，而不是静默覆盖。

录音需求如何转成产品

录音里的“场次、镜头、道具等可以调整、建实体并挂 Metadata”，被收敛为一条可验收链：来源文本 → AI 建议 → 人工决策 → 稳定实体 → 部门材料草稿。录音举过“10 场变 11 场”的插入/切分例子，但没有规定拆分算法、固定数量或本轮必须做镜头级能力。因此 Demo 只用一次处理单元切分展示关系复核，不把镜头拆分或通用自动继承包装成已完成。

2. 面试官网页的信息架构

页面采用三区工作台，并在底部保留任务台账：

区域 面试官看到什么 用户动作
左区：处理单元与进度 第四幕本次导入版本的 3 或 4 个处理单元、逐单元状态 点击锚点、观察顺序处理
中区：完整文本 本次导入的第四幕连续文本、来源说明、evidence 高亮 连续阅读、从建议回到原文
右区：建议 / 实体 AI 建议、模式、证据、人审动作；稳定实体与版本关系 编辑、采用、关联、忽略、复核
底部：任务台账 按部门组织的任务材料草稿，明确“未下发” 修改材料内容与成熟度

“完整文本”只指本次导入的第四幕连续片段，不冒充整部《雷雨》。第四幕是来源章节；3–4 个处理单元只是 API 限长、进度和失败隔离的执行边界；每条建议再用更细的 quote/range 锚定原文。

3. 从剧本到部门材料的完整 Workflow

  1. 导入与阅读：加载《雷雨》第四幕本次连续片段。正文在中区持续可见，左侧处理单元只作为导航锚点，不替换全文。
  2. 准备队列：V1 配置 3 个、V2 配置 4 个处理单元。系统按显示顺序建立队列，不宣称它们是原作场次。
  3. DeepSeek 顺序处理：用户点击“使用 DeepSeek 分析全部处理单元”后，前一单元结束才发送下一单元。真实 DeepSeek 是正式主链。
  4. 服务端校验：返回内容先经过结构、taxonomy、字段和 evidence 校验；quote 必须是当前单元的逐字子串，range 必须匹配。系统不能伪造“正在识别角色/道具”等模型内部阶段。
  5. 模式披露：校验通过的上游结果以 mode=deepseek 进入待审；缺密钥、超时、上游错误或无效输出时，以对应原因进入 mode=fallback。fallback 使用同一处理单元的确定性建议，只保障演示链，不代表 DeepSeek 成功。
  6. 人工审阅：用户查看证据、编辑建议，并选择采用为新实体、关联既有实体或忽略。点击证据只滚动并高亮原文，不触发 AI 或写入。
  7. 稳定实体：只有人工采用或关联后才形成稳定生产对象及来源关系；文本片段、建议和实体不是同一层对象。
  8. 部门任务材料：从稳定实体生成角色、场景、道具、声音、VFX 等部门材料草稿。草稿保留实体、来源和版本快照，始终显示“未下发”。
  9. V2 关系复核：V2 用一次处理单元插入/切分展示受影响关系。用户决定补入新来源或保留既有关联；系统不静默覆盖 V1，也不宣称通用自动继承。

4. 建议类型、筛选与人工边界

类型合同

分组 API 值 → UI 文案
人物 character → 角色；cast → 人物关系
场景与资产 location → 场地；set → 置景；prop → 道具；costume → 服装；makeup_hair → 妆发；wardrobe → 服装管理；vehicle → 载具；animal → 动物
拍摄与效果 vfx → 视觉特效；sfx → 现场特效；stunt → 动作特技；sound → 声音；art → 美术；camera → 摄影；lighting → 灯光
扩展 other 仅为 API 扩展值，UI 统一显示“待分类”；默认正式 fixture 不得使用

筛选的产品合同是：建议区提供“全部 + 各中文类型”的单选筛选，只过滤当前处理单元的当前建议批次，不改变建议、实体或任务。类型数量按当前批次实时计算。cast 不得显示英文原值，other 不得被包装成正式业务类型。

默认 fixture 的分类修正已在 334b0bd 验收：3 条人物关系建议与 2 个实体使用 cast，默认数据不再含 other。类型筛选以及 cast/other 的 UI 中文映射也已完成集成与浏览器验收。

人工审阅

  • 编辑：修正建议名称或制作表述，不改变其来源证据。
  • 采用新实体：把编辑后的建议固化为新的稳定生产对象。
  • 关联已有实体：复用既有 entityId，并补充来源关系，避免重复建档。
  • 忽略：保留审阅决定，但不生成实体或任务。

AI 只提供建议。它不能自动建立实体、替换人工决定、派发任务或修改剧本文本。

5. 实体与任务材料为什么分层

实体是跨版本、跨处理单元可复用的生产对象；任务材料是某一版本和来源上下文下给部门准备的草稿。一个实体可以有多条 evidence，也可以生成多份部门材料，不能把每个文本片段直接变成实体。

任务字段 是否可改 原因
任务标题 可改 需要转成部门可执行语言
制作要求 可改 需要补充规格、限制和交付说明
部门 可改 归属可能在制片判断后调整
优先级 可改 随制作风险和排期变化
材料成熟度 可改 可在“草稿 / 待复核 / 已确认”间推进
来源 不可改 是生成时的审计快照；改来源应回到实体关系复核
版本 不可改 防止草稿被误挂到另一 ScriptVersion
未下发 不可改 本 Demo 没有收件人、权限、通知、回执和撤回能力，不能伪造派发状态

6. 剧本版本化编辑：正确流程与本轮边界

完整产品不应直接在旧文本上覆盖保存，正确流程是：

编辑提案 → 创建新 ScriptVersion → 记录文本 diff → 只重新分析受影响处理单元 → 人工复核新建议与实体来源关系

这样才能保留旧版本、旧人工决定和旧任务快照。本轮只要求在 UI 的“产品边界 / 后续能力”中提供说明性入口和上述流程说明；它不能直接改写文本、保存新版本或触发重新分析。当前基线只有通用边界说明，尚未把完整流程呈现为独立入口，因此仍是未完成项，不能演示为可用功能。

7. 当前完成度

已实现于本地代码基线

  • 《雷雨》第四幕 V1 三个、V2 四个处理单元及连续全文阅读。
  • 本地 TXT 导入、处理单元导航、精确证据滚动与高亮。
  • 单次 DeepSeek API、客户端调用、严格顺序 orchestrator，以及结构/evidence 校验合同。
  • 逐单元等待、请求、DeepSeek 待审、fallback 待审、失败和取消后续请求状态。
  • 建议编辑、采用新实体、关联既有实体、忽略。
  • 稳定实体、来源关系、未下发任务材料和可编辑任务字段。
  • V1 → V2 一次处理单元切分影响及人工关系复核。
  • 默认 fixture 已移除 other，人物关系数据已改用 cast，并已与类型筛选 UI 集成验收。

“代码存在”不等于“正式 Demo 真链已验收”。线上服务端已配置 DeepSeek 并完成真实请求烟测；当前已知缺陷是模型返回内容仍可能未通过结构/证据校验，页面会明确显示 fallback · INVALID_MODEL_OUTPUT，不隐藏也不冒充成功。整版 3–4 单元稳定 deepseek 结果仍待后续优化。

演示保障

  • 每个正式处理单元都有确定性预览 / fallback 数据。
  • fallback 明示 mode、reason 和 requestId，不冒充 DeepSeek。
  • 导入文本先留在浏览器；只有用户主动分析时才逐单元发送到同源 API。
  • DeepSeek 凭证只允许存在于服务端环境，不进入前端、仓库、文档或截图。
  • 无法精确定位 quote 时显示错误，不做猜测性高亮。

明确未实现或未完成验收

  • 正式部署环境中稳定通过结构校验的 DeepSeek 全单元结果；当前真实请求可达，但烟测返回 INVALID_MODEL_OUTPUT 并诚实 fallback。
  • 不可变 AiRun / SuggestionBatch 历史，以及“重新分析本单元 / 全部”的历史 UI。
  • 剧本编辑提案、新 ScriptVersion、diff 和受影响单元重分析；当前只规划说明性入口。
  • 生产级持久化、多用户权限、审计、真实任务派发、通知、回执、更新和撤回。
  • 镜头级拆分、自动处理单元算法、任意长剧本批处理、通用 diff / 自动关系继承。
  • 中国大陆无 VPN 的现场可达性仍需用户在目标网络实测；VPN 或普通国际网络不受此项影响。

9. 面试官可能追问

为什么 AI 结果还要人工审阅？

生产判断不仅是文本抽取。隐含 VFX、声音或灯光需求需要上下文，实体复用和部门归属也属于制片决策。AI 负责缩短查找和整理时间，人工承担生产事实写入。

Extractor 算 Agent 吗？

不算。当前能力是受控输入输出的拆解流程。未来可选制片助理只有在调用查询、比对或建草稿工具时才算 Agent，而且所有写入仍需确认。

为什么 fallback 不能算模型能力？

fallback 是确定性演示保障，只证明审阅链在上游不可用时仍可走通；它不证明 DeepSeek 被调用，也不证明模型效果。

为什么任务不能点“下发”？

真实下发需要收件人、通知、权限、回执、审计、旧任务失效、更新和撤回的一致性。只加一个按钮会制造虚假生产状态，所以本轮诚实停在未下发草稿。

为什么 V2 不自动继承所有关系？

处理单元切分只是一个受控案例。通用继承需要文本 diff、实体匹配、冲突策略和审计；在这些合同没有建立前，显式影响加人工复核更可信。

为什么不直接编辑旧剧本？

原地覆盖会让证据范围、AI 建议、实体来源和任务快照同时失真。版本化编辑必须新建 ScriptVersion、记录 diff，再重分析受影响单元。

代码测试、typecheck、build 只能证明技术基线，不能替代上面的真实浏览器链和产品验收。

11. 技术与安全边界

  • 浏览器只调用同源 /api/ai/breakdown；供应商密钥由服务端环境读取。
  • 单元文本只有在用户主动点击分析后才发送；本地导入本身不上传。
  • 服务端对 taxonomy、evidence、字段长度和候选实体执行校验；不合格输出不得冒充 deepseek。
  • Demo 数据只用于面试展示，不声称生产级持久化、权限、审计或灾备。
  • 本手册不记录 API Key、Authorization、真实环境变量或私有正文。

13. 后续路线图

P1：把可信 Demo 推进到可持续试用

  • 剧本编辑提案 → 新 ScriptVersion → diff → 受影响单元重分析 → 人工复核。
  • 不可变 AiRun、UnitRun、SuggestionBatch 和重新分析历史。
  • 持久化实体、关系和任务材料，补齐基础权限与审计。
  • 完成正式部署、GitHub 交付和可重复的 DeepSeek 真链验收。

P2：扩展到真实制作协作

  • 真实任务派发、收件人、通知、回执、更新、撤回和旧任务失效策略。
  • 多用户协作、部门视图、排期、预算与资产系统集成。
  • 自动处理单元建议、镜头级结构和任意长剧本批处理。
  • 模型质量评测、Prompt 运营、成本与供应商策略。

P1/P2 都不是本轮已实现范围，不影响本次 Demo 对主链的诚实验收。
